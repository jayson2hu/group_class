# 拼课系统专家体验 Review

Date: 2026-05-10  
Status: Completed for First Improvement Round  
Method: Role-based expert walkthrough based on current PRD, implemented flows, and frontend/backend behavior  
Input: `docs/plans/2026-05-10-role-based-product-experience-research.md`  
Output Plan: `docs/plans/2026-05-10-expert-driven-product-improvement-dev-plan.md`  

---

## 1. Review 结论

当前系统已经具备“替代微信群接龙”的基础闭环：课程展示、详情、报名、候补、后台课程管理、报名管理、模板、导出、筛选、候补转正均已落地。

第一轮专家体验认为，下一阶段最值得优先做的不是新增复杂业务，而是提升三个关键转化/运营点：

1. 家长在看板和详情页的决策效率
2. 报名/候补成功后的预期清晰度
3. 运营后台对待处理报名和低质量课程的控制能力

因此，建议首批开发 K1-K5：

- K1 前台课程卡片决策信息增强
- K2 报名成功页后续预期增强
- K3 候补成功预期增强
- K4 报名列表状态筛选和待跟进视图
- K5 发布前课程完整性校验

## 2. X1：E1 家长转化体验专家

### 场景

- R1 首次接触家长：从微信群点进课程看板，1 分钟内判断是否报名
- R2 候补家长：目标课程已满员，判断是否加入候补

### 关键观察

| 页面/模块 | 观察 | 影响 |
|---|---|---|
| 前台课程卡片 | 已展示价格、人数、进度、时间，但“适合谁/课程亮点”不够显性 | 家长仍需进入详情页才能判断孩子是否适合 |
| 前台课程详情 | 信息完整，但重点信息较分散 | 焦虑型家长需要更快看到适合对象、不适合对象和亮点 |
| 报名成功页 | 已展示报名状态和课程状态，但后续动作偏泛 | 家长可能回微信群问“算报名成功了吗、多久联系、是否锁位” |
| 候补成功页 | 当前缺少候补位置/候补人数反馈 | 候补用户没有预期，容易追问运营 |
| 移动端入口 | 微信场景下用户更依赖卡片首屏判断 | 卡片信息层级影响转化 |

### 评分

| 维度 | 分数 | 原因 |
|---|---:|---|
| 决策清晰度 | 3 | 可以报名，但卡片层面对适配度表达不足 |
| 信任感 | 3 | 人数和状态有展示，后续承诺不够具体 |
| 操作效率 | 4 | 报名路径顺畅 |
| 信息完整性 | 3 | 详情页完整，卡片不够“即决策” |
| 异常处理 | 3 | 候补可用，但候补预期不足 |
| 替代微信群程度 | 3 | 仍可能因后续联系和候补位置回群追问 |

### 建议

| 优先级 | 建议 | 对应任务 |
|---|---|---|
| P0 | 看板卡片展示适合对象和亮点摘要 | K1 |
| P0 | 成功页明确后续流程、人工确认、是否锁位 | K2 |
| P0 | 候补成功返回候补人数/位置 | K3 |
| P1 | 详情页把不适合对象前移并强化 | 后续 |

## 3. X2：E2 教务运营效率专家

### 场景

运营早上处理新增报名、候补转正、导出名单，并确认课程人数变化。

### 关键观察

| 页面/模块 | 观察 | 影响 |
|---|---|---|
| 报名列表 | 已支持分页和导出，但缺少报名状态/类型筛选 | 报名多时无法快速找到候补、有效、待处理记录 |
| 报名详情 | 关键信息和备注可用 | 可以支撑单条处理 |
| 候补转正 | 功能已落地 | 但列表层面缺少“候补待处理”入口 |
| CSV 导出 | 基础字段可导出 | 可替代部分 Excel，但运营可能还需要状态筛选后导出 |
| 课程详情 | 人数变化可确认 | 操作后回看路径略长 |

### 评分

| 维度 | 分数 | 原因 |
|---|---:|---|
| 决策清晰度 | 3 | 单条清楚，批量处理不够清楚 |
| 信任感 | 4 | 数据联动基本可信 |
| 操作效率 | 3 | 缺筛选会拖慢运营 |
| 信息完整性 | 4 | 详情字段够用 |
| 异常处理 | 3 | 候补转正可用，缺历史 |
| 替代微信群程度 | 3 | 小规模可替代，大规模仍会依赖表格 |

### 建议

| 优先级 | 建议 | 对应任务 |
|---|---|---|
| P0 | 报名列表增加报名类型、报名状态、关键词筛选 | K4 |
| P1 | 增加报名操作历史 | K6 |
| P1 | CSV 支持筛选后导出和中文字段增强 | K10 |
| P1 | 增加今日待处理看板 | K9 |

## 4. X3：E3 课程供给与老师发起专家

### 场景

老师使用模板创建课程、修改关键信息、保存草稿、提交审核。

### 关键观察

| 页面/模块 | 观察 | 影响 |
|---|---|---|
| 模板管理 | 已有模板 CRUD 和模板建课入口 | 能减少从零填写 |
| 创建课程表单 | 字段完整但偏长 | 新老师可能不知道哪些必填、哪些影响转化 |
| 草稿详情 | 可提交审核 | 下一步 CTA 还可以更强 |
| 审核失败 | 当前缺少结构化驳回原因 | 老师不知道如何修改 |
| 表单质量 | 可保存低信息密度课程 | 后续审核压力较大 |

### 评分

| 维度 | 分数 | 原因 |
|---|---:|---|
| 决策清晰度 | 3 | 能建课，但缺必填/推荐字段引导 |
| 信任感 | 3 | 模板可信，审核反馈不足 |
| 操作效率 | 3 | 表单较重 |
| 信息完整性 | 4 | 字段完整 |
| 异常处理 | 2 | 驳回原因不足 |
| 替代微信群程度 | 4 | 供给结构化程度明显提升 |

### 建议

| 优先级 | 建议 | 对应任务 |
|---|---|---|
| P0 | 提交审核前做课程完整性校验 | K5 |
| P1 | 创建课程表单分步化 | K7 |
| P1 | 驳回原因结构化 | K8 |

## 5. X4：E4 平台治理与审核专家

### 场景

管理员筛选待审核课程，判断课程是否完整，审核通过或驳回。

### 关键观察

| 页面/模块 | 观察 | 影响 |
|---|---|---|
| 课程列表 | 已有状态筛选 | 可以找到待审核 |
| 课程详情 | 可查看负责人、封面、亮点等字段 | 有审核基础 |
| 提交审核 | 缺少完整性门槛 | 低质量课程可能进入审核队列 |
| 审核驳回 | 缺少原因字段 | 影响老师修改效率 |
| 权限 | 基础角色隔离可用 | MVP 可接受 |

### 评分

| 维度 | 分数 | 原因 |
|---|---:|---|
| 决策清晰度 | 3 | 可审核，但缺质量清单 |
| 信任感 | 3 | 发布质量依赖人工 |
| 操作效率 | 3 | 可筛选，但审核信息未评分 |
| 信息完整性 | 3 | 字段在，但缺完整性判断 |
| 异常处理 | 3 | 取消/驳回存在，原因不足 |
| 替代微信群程度 | 4 | 发布控制比微信群强 |

### 建议

| 优先级 | 建议 | 对应任务 |
|---|---|---|
| P0 | 提交审核前阻止关键信息不完整课程 | K5 |
| P1 | 审核详情增加完整性评分 | 后续 |
| P1 | 驳回原因结构化 | K8 |

## 6. X5：E5 业务经营与增长专家

### 场景

校区负责人每周查看课程状态，判断哪些课程需要推动，是否替代微信群接龙。

### 关键观察

| 页面/模块 | 观察 | 影响 |
|---|---|---|
| 课程列表 | 可按状态筛选，能看到人数 | 能找到即将成班课程 |
| 报名数据 | 可导出，但缺聚合分析 | 经营判断仍要二次处理 |
| 负责人字段 | 已有 ownerId | 还没有进入聚合视图 |
| 运营动作 | 缺少“差几人成班/报名停滞/候补多”的聚合提示 | 负责人需要人工判断 |
| 模板效果 | 暂无模板维度分析 | 不知道哪个模板转化好 |

### 评分

| 维度 | 分数 | 原因 |
|---|---:|---|
| 决策清晰度 | 3 | 单课程可判断，整体经营弱 |
| 信任感 | 4 | 基础数据可信 |
| 操作效率 | 2 | 经营分析依赖导出 |
| 信息完整性 | 3 | 缺聚合指标 |
| 异常处理 | 3 | 缺主动提醒 |
| 替代微信群程度 | 3 | 替代接龙，但未替代经营报表 |

### 建议

| 优先级 | 建议 | 对应任务 |
|---|---|---|
| P1 | 运营看板 MVP | K9 |
| P1 | CSV 字段增强 | K10 |
| P2 | 经营数据分析看板增强 | K14 |

## 7. X6：E6 移动端可用性与可访问性专家

### 场景

375px 移动端、微信入口、长列表、高数据量后台。

### 关键观察

| 页面/模块 | 观察 | 影响 |
|---|---|---|
| 前台看板 | 卡片信息密度适中，但新增信息需谨慎 | K1 需要限制摘要长度 |
| 详情页底部 CTA | 有固定底部操作区 | 移动端转化友好 |
| 分享链接 | 已有复制和降级展示 | HTTP/微信环境可继续验证 |
| 后台筛选 | 已有课程筛选，报名缺筛选 | 高数据量报名处理弱 |
| 表单 | 字段多，移动端会较长 | 后续适合分步化 |

### 评分

| 维度 | 分数 | 原因 |
|---|---:|---|
| 决策清晰度 | 3 | 移动端可用但卡片适配信息不足 |
| 信任感 | 3 | 流程可用 |
| 操作效率 | 3 | 表单较长 |
| 信息完整性 | 3 | 移动端需要摘要 |
| 异常处理 | 3 | 降级路径存在 |
| 替代微信群程度 | 3 | 微信传播可用，体验还需人工实测 |

### 建议

| 优先级 | 建议 | 对应任务 |
|---|---|---|
| P0 | K1 信息摘要需移动端友好 | K1 |
| P0 | 报名列表筛选提升后台高负载可用性 | K4 |
| P1 | 创建课程表单分步化 | K7 |

## 9. 首轮开发建议

按以下顺序执行：

1. K1 前台课程卡片决策信息增强
2. K2 报名成功页后续预期增强
3. K3 候补成功预期增强
4. K4 报名列表状态筛选和待跟进视图
5. K5 发布前课程完整性校验

每个任务都应单独开发、单独自测、单独更新计划、单独提交。
