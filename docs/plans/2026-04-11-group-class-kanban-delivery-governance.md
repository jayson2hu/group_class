## 1. 文档目的

本文件用于定义拼课课程系统从需求、设计、开发、测试、验收、审批到交付的统一研发治理规范。

目标不是“把功能做出来”，而是：
1. 严谨设计
2. 并行推进
3. 小步快跑
4. 每步可验证
5. 每步有记录
6. 问题可追踪
7. 文档与进度持续同步
8. 最终由 Hermes 进行阶段性审批与总体验收汇报

---

## 2. 基本研发原则

### 2.1 先设计，后开发
任何 Batch 在进入开发前，必须先完成对应设计文档，并通过设计评审。

必须至少包含：
1. 前端/UI设计文档
2. 后端/架构设计文档
3. 接口/数据契约说明
4. 测试与验收清单

### 2.2 可并行则并行
在依赖关系允许的前提下，前后端设计、前后端开发、测试准备、文档编写应尽量并行，以提高整体效率。

### 2.3 小功能点闭环交付
每一个小功能点必须完成以下动作后，才允许标记完成：
1. 开发完成
2. 开发者自测完成
3. 记录自测结果
4. 记录验收结果
5. 更新问题清单
6. 更新进度文档
7. 通过审批

### 2.4 文档与代码同等重要
任何功能状态变更，必须同步到文档；任何问题和风险，必须及时记录；任何阶段结果，必须可追溯。

### 2.5 严格质量门禁
未完成自测、未补文档、未更新进度、未记录问题的功能点，不得进入“已完成”状态。

## 3. 角色分工

## 3.1 产品负责人（Product）
职责：
- 维护 PRD
- 明确范围与优先级
- 管理需求变更
- 对业务验收口径负责

交付物：
- PRD
- 范围说明
- 验收标准
- 变更记录

## 3.2 UI 设计师（Designer）
职责：
- 负责前端信息架构、页面结构、交互说明、视觉规范
- 输出前台页面与后台页面的 UI/UX 设计说明
- 对关键交互和状态展示负责

交付物：
- 前端/UI设计文档
- 页面清单
- 页面结构与交互说明
- 状态展示规范
- 表单校验与反馈规范

## 3.3 后端架构师（Architect）
职责：
- 负责后端架构、模块划分、数据结构、权限模型、状态流转、接口契约
- 负责非功能约束与演进策略

交付物：
- 后端/架构设计文档
- 数据模型设计
- 权限模型设计
- 状态机设计
- API/事件/数据契约

## 3.4 开发工程师（Frontend / Backend）
职责：
- 按设计与任务单实现功能
- 每个小功能点先自测后提交
- 更新实施记录与问题清单

交付物：
- 代码实现
- 自测记录
- 变更说明
- 小功能点完成说明

## 3.5 QA / 验收角色
职责：
- 按功能点执行验收
- 核对是否满足 PRD、设计文档、测试标准
- 输出验收记录与缺陷

交付物：
- 验收记录
- 缺陷记录
- 回归结果

## 3.6 Hermes（审批者 / 流程协调者）
职责：
- 审批设计是否可进入开发
- 审批功能点是否可标记完成
- 审批批次是否可进入下一阶段
- 汇总最终交付结果给用户

审批权限：
- 设计评审通过 / 驳回
- 功能点完成通过 / 驳回
- Batch 完成通过 / 驳回
- 最终交付通过 / 驳回

## 5. 批次执行前置要求

任一 Batch 开始前，必须满足：

### 5.1 设计前置
- PRD 已明确本批次范围
- UI 设计文档已完成对应页面设计
- 架构设计文档已完成对应后端方案
- 测试与验收文档已列出本批次验收项

### 5.2 任务前置
- 本批次已拆分为可独立验收的小功能点
- 已识别可并行任务与依赖任务
- 已指定每个任务的责任角色

### 5.3 文档前置
- issue log 已初始化
- progress 文档已初始化
- 每个 batch 的入口、出口标准已写清楚

如未满足上述条件，Hermes 不批准进入开发。

## 6. 并行开发规则

## 6.1 可并行内容
允许并行：
1. UI设计 与 架构设计
2. 前端开发 与 后端开发（基于已冻结契约）
3. 测试用例准备 与 功能开发
4. 文档更新 与 开发推进

## 6.2 并行前提
并行开发前必须先冻结以下内容：
- 数据结构关键字段
- API 输入输出契约
- 状态流转定义
- 权限边界
- 页面字段与交互规则

如果契约未冻结，不允许盲目并行开发。

## 6.3 并行组织方式
建议按以下工作流组织：
- 设计流 A：UI 设计师产出页面与交互设计
- 设计流 B：架构师产出后端与接口设计
- 开发流 A：前端按 UI 与 API 契约开发
- 开发流 B：后端按架构与 API 契约开发
- 验收流：QA/Hermes 根据测试与验收文档逐项验证

## 7. 小功能点交付规范

每个小功能点必须最小化、可独立验收，例如：
- 后台课程列表页基础展示
- 新建课程页基础字段保存
- 草稿保存接口
- 提交审核按钮与状态流转
- 前台课程卡片展示
- 报名表单提交

### 7.1 小功能点完成标准
一个小功能点必须至少包含以下七步：
1. 明确功能点范围
2. 实现代码
3. 开发者自测
4. 记录自测结果
5. 进行验收
6. 更新 issue log 与 progress
7. Hermes 审批通过

### 7.2 自测记录要求
每个功能点必须记录：
- 功能点名称
- 涉及文件
- 自测环境
- 自测步骤
- 自测结果
- 已知限制

### 7.3 验收记录要求
每个功能点必须记录：
- 验收依据（PRD / UI / Architecture / Test doc）
- 验收步骤
- 验收结果
- 是否通过
- 未通过项
- 后续处理建议

---

## 8. 问题记录规范

## 8.1 必须记录的问题类型
以下问题必须进入 issue log：
1. 需求不明确
2. 设计冲突
3. 技术阻塞
4. 测试失败
5. 验收不通过
6. 延期风险
7. 依赖风险

## 8.2 issue log 字段建议
- Issue ID
- 日期
- 所属 Batch
- 所属功能点
- 问题描述
- 问题类型
- 影响范围
- 当前状态
- 负责人
- 解决方案 / 下一步

### 8.3 问题处理要求
- 发现即记录
- 状态变化即更新
- 关闭必须注明解决方式
- 批次结束前必须复查未关闭问题

---

## 9. 进度同步规范

## 9.1 progress 文档必须同步的内容
- 当前批次
- 当前并行流
- 当前功能点状态
- 已完成项
- 进行中项
- 阻塞项
- 下一步计划
- 最近更新人 / 更新时间

## 9.2 更新时间要求
以下情况必须更新进度文档：
1. Batch 启动
2. 小功能点开始开发
3. 小功能点开发完成
4. 自测完成
5. 验收完成
6. 遇到阻塞
7. Batch 完成

---

## 10. 文档更新规范

文档不是阶段性补写，而是过程实时维护。

### 10.1 必须实时更新的文档
- PRD（范围变更时）
- UI 设计文档（页面或交互调整时）
- 架构设计文档（接口/数据模型调整时）
- 测试与验收文档（新增功能点时）
- issue log（发现问题时）
- progress（状态变更时）

### 10.2 更新原则
- 先更新设计，再更新实现
- 先记录问题，再处理问题
- 先同步状态，再宣称完成

---

## 11. 严谨开发规范

## 11.1 工程规范
- 优先复用现有架构与规范
- 严禁平行造轮子
- 保持模块职责清晰
- 尽量避免跨层耦合
- 变更应最小闭环

## 11.2 代码规范
- 命名明确
- 接口入参与出参清晰
- 状态枚举统一定义
- 权限校验前后端一致
- 错误处理明确
- 日志可追踪

## 11.3 测试规范
- 每个功能点必须至少有最小验证方式
- 关键流程必须覆盖正向路径
- 权限与状态流转必须重点验证
- 修复 bug 后必须补最小回归验证

## 11.4 变更规范
- 每次变更需说明影响范围
- 有接口变更必须同步契约文档
- 有状态变更必须同步状态说明
- 有字段变更必须同步数据结构说明

## 12. 审批流程

## 12.1 设计审批
进入开发前，Hermes 审批以下内容：
- UI 设计文档是否完整
- 架构设计文档是否完整
- 测试与验收清单是否完整
- 可并行边界是否明确

审批结果：
- Approved：可进入开发
- Rejected：补齐后重提

## 12.2 功能点审批
小功能点完成后，Hermes 审批以下内容：
- 是否按需求实现
- 是否完成自测
- 是否有验收记录
- 是否更新 issue log
- 是否更新 progress

审批结果：
- Approved：可标记完成
- Rejected：退回补充

## 12.3 Batch 审批
Batch 完成后，Hermes 审批以下内容：
- 功能范围是否闭环
- 文档是否同步完整
- 问题是否已记录与分级
- 未关闭问题是否可接受
- 是否允许进入下一个 Batch

## 12.4 最终审批
最终交付前，Hermes 进行总结审批并向用户汇报：
- 总体实现范围
- 已完成批次
- 未完成事项
- 风险与遗留问题
- 建议下一步

## 14. 对本项目的直接执行要求

从现在开始，本项目执行必须遵守以下追加要求：

1. 每个 Batch 开始前，先产出：
   - UI 设计文档
   - 架构设计文档
   - 测试与验收文档
   - issue log
   - progress 文档

2. 能并行的工作必须优先并行拆分。

3. 每个小功能点完成后，必须：
   - 自测
   - 验收
   - 写记录
   - 更新进度
   - 更新问题日志

4. Hermes 拥有阶段审批权与最终审批权。

5. 对用户的最终汇报，必须基于已审批通过的结果，而非仅开发完成的结果。
