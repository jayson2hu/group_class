## 1. 目的

本文件用于把《拼课课程看板与创建管理系统 PRD》落成可执行的 ACPX 分批开发计划，方便后续通过 `acpx` 或 ACP 兼容代理（如 Claude Code、Codex、OpenCode）按批次推进开发。

本计划默认遵守《拼课课程系统研发治理与交付规范》，即：
1. 先设计，后开发
2. 前后端分别设计
3. 可并行则并行
4. 每个小功能点先自测，再验收，再审批
5. 问题、进度、文档实时同步
6. Hermes 拥有阶段审批权与最终审批权

---

## 2. 强制交付流程总览

每个 Batch 必须按照以下流程推进：

### Phase A：设计阶段（先于开发）
必须先产出并评审：
1. UI 设计文档（Designer）
2. 后端/架构设计文档（Architect）
3. 测试与验收文档（QA/Test）
4. issue log 初始化
5. progress 文档初始化

### Phase B：开发阶段（允许并行）
在接口契约、状态定义、权限边界冻结后，可并行推进：
1. 前端开发
2. 后端开发
3. 测试用例准备
4. 文档同步更新

### Phase C：小功能点闭环
每个小功能点必须按以下顺序完成：
1. 开发实现
2. 开发者自测
3. 记录自测结果
4. 执行验收
5. 记录验收结果
6. 更新 issue log
7. 更新 progress
8. Hermes 审批

### Phase D：Batch 审批
- 汇总所有小功能点结果
- 审核未关闭问题
- 审核文档完整性
- Hermes 决定是否允许进入下一个 Batch

## 3. 推荐开发顺序总览

### Batch 0：设计与治理初始化
目标：完成执行前所有设计与治理准备，冻结并行开发边界。

### Batch 1：数据模型与后台课程管理骨架
目标：让系统具备“能创建课程草稿并管理”的基础能力。

### Batch 2：角色权限与审核发布流
目标：让“管理员 / 指定发起人创建课程”的机制真正成立。

### Batch 3：前台课程看板与详情页
目标：让用户能看到课程并完成选择。

### Batch 4：报名、候补、报名管理
目标：打通从前台报名到后台查看的闭环。

### Batch 5：模板能力与运营效率增强
目标：提高课程创建效率，减少重复配置。

### Batch 6：增强项（可选）
目标：为后续转化率与自动化能力做增强。

## 12. 推荐 ACPX 执行方式

## 12.1 设计阶段执行模式
建议先用 acpx 生成 / 完善设计类文档：

```bash
acpx claude "阅读 PRD 与治理规范，作为 UI 设计师输出 UI 设计文档"
acpx claude "阅读 PRD 与治理规范，作为架构师输出架构设计文档"
acpx claude "阅读 PRD 与治理规范，输出测试与验收文档、issue log、progress 初始化内容"
```

## 12.2 开发阶段执行模式
设计冻结后，按批次推进，并在前后端允许时并行拆分：

```bash
acpx claude "执行 Batch 1 Track 1A：后端开发..."
acpx claude "执行 Batch 1 Track 1B：前端开发..."
```

## 12.3 推荐工作流
1. Hermes/你确认当前 batch 范围。
2. 先完成设计与治理文档。
3. Hermes 审批设计通过。
4. `acpx` 按并行 track 执行当前 batch。
5. 每个小功能点自测、验收、更新文档。
6. Hermes 审批通过后进入下一功能点/下一 batch。

---

## 13. 每批次交付要求

要求 acpx 每次交付时必须输出：
1. 修改文件清单
2. 小功能点完成清单
3. 自测结果
4. 验收结果
5. 数据结构/接口变更说明
6. issue log 更新内容
7. progress 更新内容
8. 尚未覆盖的边界
9. 需要 Hermes 审批的事项

---

## 14. 风险控制建议

1. 不要一开始把支付、通知、推荐都并进 MVP。
2. 审核流和权限必须同时在接口层实现，不能只做前端显示控制。
3. 状态逻辑要统一定义，避免前台与后台判断不一致。
4. 如果项目已有鉴权或后台框架，优先复用，不要另起一套。
5. 每一批都要可回归，不要等所有批次做完再整体验证。
6. 并行开发前必须先冻结契约，否则效率会变成返工。
